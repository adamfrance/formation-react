L'API du cours : un vrai serveur Express

Le concept

Une application React ne garde presque rien chez elle : l'annuaire, les produits, la connexion viennent d'un serveur, l'API, comme une cuisine qui sert la salle d'un restaurant. Pendant trois jours, cette API tourne sur votre poste : le dossier api/, à l'adresse http://localhost:4000. C'est un vrai serveur Express qui reproduit l'API publique de test DummyJSON : mêmes adresses, mêmes réponses, mêmes comptes. On le lance chaque matin, on ne le modifie pas.

Les ressources : chaque liste de données a son adresse (/users, /products, /todos, /posts, /carts, /comments), avec pagination (limit, skip), choix des champs (select), tri (sortBy) et recherche (/users/search?q=).

Trombi lit /users (208 collaborateurs) et leurs tâches ; la Marketplace lit /products (194 produits) et passe ses commandes sur /carts. Un identifiant inconnu (/users/999) donne 404.

Les écritures simulées : POST, PUT, PATCH et DELETE répondent comme si l'opération avait réussi, mais rien n'est enregistré ; l'API reste la même pour tout le monde.

La connexion : POST /auth/login avec un compte de démonstration (emilys / emilyspass, administratrice ; averyp / averyppass, utilisateur) renvoie un jeton ; elle sert au jour 2.

?delay=1500 : ajouté à n'importe quelle adresse, il fait attendre la réponse 1,5 seconde ; pratique pour voir les écrans de chargement.

Ses protections : comme une API d'entreprise, elle limite le nombre de requêtes (100 par 10 secondes, puis une erreur 429), n'accepte que les applications du cours et répond toujours en JSON. Le détail est dans api/README.md.

Dans src/, un dossier par rôle :

Le trajet d'une requête : quand Trombi demande GET /users?limit=2, la requête traverse ces dossiers dans l'ordre :

  1. middlewares/ : les protections (en-têtes de sécurité, applications autorisées, limite de débit), puis l'attente si l'adresse contient ?delay= ;
  2. routes/ : l'adresse /users mène au contrôleur des ressources ;
  3. schemas/ : le contrôle de la requête, limit=2 est bien un nombre ;
  4. controllers/ : le contrôleur lit les paramètres et appelle le service des listes ;
  5. services/ : le service applique la pagination, le tri et le choix des champs ;
  6. repositories/ : les 208 utilisateurs, déjà en mémoire ;
  7. le contrôleur renvoie la réponse en JSON. Une erreur, à n'importe quelle étape, arrive dans middlewares/errors.js, qui répond { "message": … } avec le bon statut (400, 401, 404, 429).

C'est le découpage qu'on retrouve dans la plupart des API Express : une adresse dans routes/, une règle dans services/, une donnée dans repositories/.

En résumé : une API sur votre poste qui répond comme DummyJSON : des listes à lire (/users, /products…), des écritures simulées, une connexion par jeton, une limite de débit ; on la lance le matin (npm start dans api/) et on ne la modifie pas.

Dans la vraie vie : toute application React parle à une API de ce genre, écrite par l'équipe back-end : on lit sa documentation, on respecte ses limites et on traite ses erreurs.

L'écosystème JavaScript moderne

L'écosystème JavaScript en 2026

Le concept

Une cuisine de restaurant : le client ne voit que l'assiette, mais derrière, des commis épluchent, cuisent et dressent. Le navigateur est le client : il ne comprend que le JavaScript. On écrit du TypeScript avec du JSX, une syntaxe proche du HTML (fichiers .tsx), et des outils les traduisent avant de les lui servir.

Node.js : exécute du JavaScript hors du navigateur ; c'est lui qui fait tourner npm, Vite et TypeScript (version 22 ou 24).

npm : installe les bibliothèques dans node_modules/ et lance les scripts de package.json.

pnpm et Yarn font le même travail ; une équipe en choisit un.

Vite : le serveur de développement et l'outil de construction (build). Pendant le développement, il traduit chaque fichier à la volée et met la page à jour à chaque enregistrement ; pour la production, il assemble tout en quelques fichiers optimisés.

Oxc : le transpileur intégré à Vite 8 ; il traduit TypeScript et JSX en JavaScript. Babel, SWC et esbuild font le même travail dans d'autres outils.

TypeScript : ajoute des types à JavaScript et les vérifie avant l'exécution.

Oxlint : le vérificateur de code (linter, comme ESLint) ; npm run lint signale les erreurs courantes. Prettier met le code en forme ; il est facultatif.

En résumé : Node.js fait tourner les outils, npm les installe, Vite sert et construit l'application, TypeScript vérifie les types, Oxlint relit le code.

Dans la vraie vie : tous les jours ; tout projet front d'entreprise a cette chaîne (serveur de développement, build dans l'intégration continue, vérificateur de code avant chaque fusion), et savoir lire package.json et lancer ses scripts suffit pour reprendre un projet en quelques minutes.

Vite ou Create React App

Le concept

Create React App est un modèle de voiture qu'on ne fabrique plus : il roule encore, mais plus personne ne le répare.

Create React App : l'ancien outil de création de projets React, arrêté par l'équipe React en février 2025. On le reconnaît dans un vieux projet ; on n'en crée plus.

Vite : crée et sert une application qui tourne dans le navigateur, notre cas. Son serveur démarre en moins d'une seconde, et seul le fichier modifié est retraduit.

Next.js : un framework construit sur React, pour un site dont les pages doivent être produites par le serveur (jour 3).

Vite Create React App
État maintenu, version 8 (mars 2026) abandonné (février 2025)
Démarrage du serveur moins d'une seconde plusieurs secondes, de plus en plus lent avec la taille du projet
Rechargement après une modification instantané (seul le fichier modifié est retraduit) reconstruit le paquet
Construction Rolldown (Rust) Webpack
Configuration vite.config.ts, courte et modifiable cachée (il fallait « éjecter »)

En résumé : Vite pour une application qui tourne dans le navigateur, Next.js quand le serveur doit produire les pages, Create React App seulement pour le reconnaître.

Dans la vraie vie : les nouveaux projets partent de Vite ou d'un framework ; migrer une application Create React App vers Vite est un chantier courant, souvent confié à un nouvel arrivant (une demi-journée pour un projet moyen).

TypeScript : l'essentiel pour React

Le concept

Une étiquette sur chaque carton d'un déménagement : « vaisselle », « livres ». Sans elle, on découvre le problème en ouvrant le carton ; avec elle, on le voit avant. TypeScript colle une étiquette, un type, sur chaque donnée, et vérifie tout le code avant l'exécution : une faute de frappe dans un nom de champ est signalée tout de suite, au lieu d'afficher undefined en production.

interface : décrit la forme d'un objet, ses champs et leurs types.

Pratique pour décrire les données d'une API et les props d'un composant, les deux usages principaux en React.

Les types simples et les tableaux : number, string, boolean, et Personnage[] pour un tableau. Le type se déduit souvent tout seul : let count = 0 est un number.

Le générique : précise le type de ce qu'une fonction manipule, entre chevrons.

import type : importe seulement un type ; rien n'arrive dans le JavaScript produit.

npm run dev ne vérifie pas les types : Vite les retire pour aller vite. La vérification se fait dans l'éditeur (soulignés rouges), avec npx tsc -b, et automatiquement avant chaque npm run build.

En résumé : interface pour la forme d'un objet, ? pour un champ facultatif, | pour une liste de valeurs, <…> pour préciser un générique, import type pour les types ; TypeScript vérifie tout avant l'exécution.

Dans la vraie vie : tous les jours ; TypeScript est la norme des nouveaux projets React, et le fichier des types de l'API est souvent généré à partir de sa documentation (OpenAPI).

Les principes fondamentaux de React

Pourquoi React

Le concept

Le tableau des départs d'une gare : personne ne repeint à la main les lignes qui changent ; on lui donne la liste des trains, et il affiche ce qu'il faut. Sans React, chaque action oblige à retrouver les bons éléments de la page (document.querySelector) et à les modifier un par un : un collaborateur passe en favori, et il faut mettre à jour son étoile, le compteur, la liste filtrée et la fiche ouverte ; un oubli, et l'écran ment.

L'interface est une fonction de l'état : on décrit l'écran pour des données, et React le met à jour quand elles changent.

Les composants : l'interface est découpée en fonctions qui renvoient du JSX (CollaboratorCard, Header), écrites une fois, utilisées partout.

Le flux à sens unique : les données descendent du parent vers l'enfant (les props) ; l'enfant prévient le parent en appelant une fonction reçue.

Le DOM virtuel : React calcule l'interface en mémoire, la compare à la précédente, puis ne modifie dans la page que ce qui a changé ; la recherche réaffiche 208 cartes sans tout reconstruire.

Une bibliothèque : React ne s'occupe que de l'interface ; le routage, l'état global et les appels réseau viennent d'autres bibliothèques (React Router, Redux Toolkit, React Query : jours 2 et 3) ou d'un framework construit sur React, comme Next.js. Créé chez Facebook en 2011, publié en 2013 ; documentation : react.dev (fr.react.dev en français).

En résumé : on décrit l'écran pour un état, en composants ; les données descendent, les actions remontent, et React applique seulement les différences.

Dans la vraie vie : tous les jours ; React est la bibliothèque d'interface la plus utilisée en entreprise (applications métier, tableaux de bord, back-offices, React Native pour le mobile), et penser « interface = fonction de l'état » sert aussi avec Vue ou Angular.

JSX : syntaxe et bonnes pratiques

Qu'est-ce que JSX

Le concept

Le JSX ressemble à du HTML, mais c'est une écriture abrégée, comme la sténo : avant d'arriver au navigateur, Vite la retranscrit en JavaScript ordinaire.

Le JSX : une balise dans du JavaScript ; elle devient un appel de fonction qui fabrique un élément React, un petit objet qui décrit ce qu'on veut afficher.

Vite compile la balise en jsxs('h1', { className: 'titre', children: ['Bonjour ', name, ' !'] }) ; React se sert ensuite de l'élément pour mettre la page à jour.

Les accolades {} : on y place n'importe quelle expression JavaScript (une variable, un calcul, un appel de fonction), jamais une instruction comme if ou for.

La majuscule : une balise en minuscule (<h1>) est un élément HTML ; une balise qui commence par une majuscule (<App />) est un composant.

Le programme cite React.createElement : c'était la traduction jusqu'à React 17 (2020). Aujourd'hui, jsx() est importé automatiquement, et on n'écrit plus import React en haut des fichiers.

En résumé : une balise JSX devient un appel jsx() qui décrit l'écran ; {} pour une expression ; majuscule pour un composant.

Dans la vraie vie : on écrit du JSX tous les jours et on ne lit jamais sa traduction, sauf en déboguant le code produit ; React.createElement ne se croise plus que dans du code ancien.

Le concept

Le DOM virtuel et la réconciliation

DOM virtuel, réconciliation et clé key

Le concept

Un architecte qui transforme une maison ne la rase pas : il compare l'ancien plan et le nouveau, et ne fait refaire que ce qui change.

Le DOM virtuel : l'interface calculée en mémoire, sous forme de simples objets JavaScript. Modifier la vraie page coûte cher ; calculer des objets ne coûte presque rien.

La réconciliation : React compare le nouvel arbre au précédent, puis n'applique au vrai DOM que les différences.

  • Même type d'élément au même endroit (<li> puis <li>) : React garde l'élément du DOM et met à jour ses attributs.
  • Type différent (<li> puis <div>, ou un composant remplacé par un autre) : React supprime l'ancien sous-arbre et en crée un nouveau ; l'état de l'ancien est perdu.

key : identifie un élément parmi ses frères ; React associe les éléments d'une liste par leur clé, et un élément qui garde sa clé garde son DOM et son état, même s'il change de place.

Unique dans la liste, stable d'un rendu à l'autre : un identifiant venu des données est la bonne clé ; l'indice ne convient que si la liste ne change jamais d'ordre ; Math.random() est la pire, car tout est recréé à chaque rendu.

En résumé : React calcule l'interface en mémoire, compare, et ne modifie que les différences ; dans une liste, la key dit quel élément est lequel.

Dans la vraie vie : on n'écrit jamais la réconciliation, mais les bogues de clé sont classiques dans les listes qu'on trie ou qu'on filtre (un champ qui « saute » d'une ligne à l'autre) : en revue de code, on vérifie les key.

Le concept

Un cadre photo : le cadre est toujours le même, on glisse dedans la photo qu'on veut.

Styler un composant

Le concept

Dans une colocation, une étiquette « lait » sur le frigo commun peut désigner la bouteille d'un autre ; une boîte à son nom, dans son placard, ne prête jamais à confusion. Le CSS a le même problème : dans une feuille globale, toutes les classes partagent le même espace, et deux composants qui utilisent .title se marchent dessus.

Le CSS global : une feuille importée une fois, dont les classes valent partout ; pour le thème (les variables), la mise en page générale et les classes partagées.

Les CSS Modules : un fichier Carte.module.css à côté du composant ; Vite renomme chaque classe pour la rendre unique (card devient _card_bqs0q_1).

Pratique pour le style propre à un composant : il ne déborde jamais sur un autre.

Le style en ligne : un objet JavaScript dans la prop style, de type CSSProperties ; pour une valeur calculée ou venue des données.

Tailwind (className="rounded-lg border p-4") et CSS-in-JS (styled-components, Emotion) : deux autres approches qu'on croise en entreprise ; la seconde est moins adaptée aux Server Components (jour 3).

Le CSS de Trombi est fourni : on le copie, on ne l'écrit pas. Ce qu'on apprend ici, c'est où le ranger et comment l'appliquer dans le JSX.

En résumé : le CSS global pour le thème, les CSS Modules pour le style d'un composant, le style en ligne pour les valeurs calculées.

Dans la vraie vie : CSS Modules et Tailwind dans les nouveaux projets, styled-components dans ceux des années 2018 à 2022 ; une équipe choisit une approche principale et garde le style en ligne pour les valeurs calculées.

Les événements

Le concept

On branche une sonnette une fois pour toutes ; elle sonne quand quelqu'un appuie.

onClick : branche une fonction sur le clic. On passe la fonction, on ne l'appelle pas : onClick={handleClick} sonne au clic, onClick={handleClick()} sonne tout de suite, au rendu. Pour passer un argument, on enveloppe la fonction.

onChange : appelé à chaque frappe dans un champ ; event.target.value donne le texte.

onSubmit : appelé à l'envoi d'un formulaire ; event.preventDefault() empêche le navigateur de recharger la page.

Le type de l'événement se déduit quand la fonction est écrite dans la prop ; on l'écrit quand elle est déclarée à part.

Événement Prop Type de l'objet événement
clic onClick MouseEvent<HTMLButtonElement>
saisie dans un champ onChange ChangeEvent<HTMLInputElement>
envoi d'un formulaire onSubmit SubmitEvent<HTMLFormElement>
sortie d'un champ onBlur FocusEvent<HTMLInputElement>
touche du clavier onKeyDown KeyboardEvent (event.key === 'Enter')

event.stopPropagation() : un clic remonte vers les parents de l'élément, comme une bulle ; stopPropagation l'arrête. Utile quand une ligne cliquable contient un bouton (supprimer, favori).

Le programme utilise React.FormEvent pour onSubmit : les types de React 19.3 le remplacent par SubmitEvent.

En résumé : une prop onQuelqueChose reçoit une fonction ; event.target.value pour un champ, preventDefault pour un formulaire, stopPropagation pour arrêter la remontée.

Dans la vraie vie : tous les jours ; le bouton jour / nuit et la recherche « à la frappe » sont dans presque toutes les applications, et la propagation se règle dès qu'une ligne cliquable contient un bouton.

TP

useState : la recherche et le thème

Le concept

Un composant est une fonction : React l'appelle à chaque rendu, et ses variables repartent de zéro, comme un serveur sans carnet qui oublie la commande entre deux passages. L'état est le carnet : React garde la valeur pour le composant, la lui rend au rendu suivant, et refait le rendu quand elle change.

useState : donne la valeur actuelle et la fonction pour la changer ; la nouvelle valeur arrive au rendu suivant.

Juste après setTheme, theme garde l'ancienne valeur dans la fonction en cours.

Le champ contrôlé : sa valeur vient de l'état (value) et chaque frappe met l'état à jour (onChange) ; on peut alors le vider, le valider ou le préremplir.

La valeur dérivée : ce qui se calcule à partir de l'état se calcule au rendu, sans état de plus.

Les règles des hooks : on appelle useState (et tout hook) en haut du composant, toujours dans le même ordre, jamais dans une condition ni une boucle.

En résumé : useState pour ce qui change et doit être retenu, un champ contrôlé pour la saisie, une valeur dérivée pour tout ce qui se calcule.

Dans la vraie vie : tous les jours ; recherches et filtres « à la frappe » sont dans toutes les listes (clients, commandes, produits), et ne pas stocker ce qui se calcule évite la plupart des affichages incohérents.

Les effets avec useEffect

TP

Charger l'annuaire depuis l'API

Le concept

Au restaurant, on donne d'abord la carte au client, puis on passe la commande en cuisine ; le plat arrive plus tard. Un composant qui charge des données fait pareil : il s'affiche tout de suite (« Chargement… »), puis, après l'affichage, un effet va chercher les données ; quand elles arrivent, l'état change et le composant se réaffiche.

useEffect : exécute du code après l'affichage, pour se synchroniser avec l'extérieur (une API, le DOM, le stockage du navigateur) ; le tableau [], les dépendances, veut dire : une seule fois, après le premier rendu.

On n'appelle jamais fetch dans le corps du composant : il est exécuté à chaque rendu, chaque réponse provoquerait un rendu, qui relancerait une requête, sans fin.

Les trois états : chargement, succès, erreur ; l'écran affiche l'un des trois.

response.ok : fetch ne rejette sa promesse qu'en cas de panne réseau ; un 404 ou un 500 arrive dans .then, on teste response.ok et on lance l'erreur soi-même.

La fonction passée à useEffect ne peut pas être async : on enchaîne .then, ou on déclare une fonction async à l'intérieur et on l'appelle.

En résumé : useEffect(…, []) pour charger après le premier affichage, trois états (chargement, succès, erreur), et response.ok testé à chaque réponse.

Dans la vraie vie : souvent au début d'un projet, puis de moins en moins : on charge les données avec React Query (jour 3), qui écrit cet effet à notre place ; fetch suffit, on croise axios dans le code plus ancien.
